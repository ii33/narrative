# 属性分类

大类回答「这句话在说对象的哪个方面」；`scope` 回答「这是谁的记录」。
两件事各管一件事，互不替代：`林舟以为老周受伤了` 仍然记在「能力与身体状态」，
只是 `scope = cognition`、`holder = 林舟`。

分类是**整理手段**，不是事实判断。它只决定这条披露显示在哪个标题下面，
不改变取值、不改变披露顺序、不改变原文引文。

## 默认分类表

按对象类型给一套默认大类；用户可改名、增减，保存在工程库里（`meta.property_categories`），
「其他」始终在最后且不能删除。

| 类型 | 大类 |
| --- | --- |
| 人物 | 基本信息 · 外貌 · 身份与经历 · 能力与身体状态 · 持有与使用 · 关系 · 心理与意图 · 其他 |
| 物品 | 基本信息 · 外观与构造 · 功能与特性 · 状态 · 归属与持有 · 关联 · 其他 |
| 群体 | 基本信息 · 构成与规模 · 实力与资源 · 立场与关系 · 状态 · 其他 |
| 地点 | 基本信息 · 环境与外观 · 位置与范围 · 势力与居住者 · 状态 · 其他 |
| 事件 | 基本信息 · 参与者 · 过程与结果 · 其他 |
| 场景 | 基本信息 · 内容 · 其他 |

「基本信息」而不是「固有」：姓名、年龄、身份、种族在作品里都可能变化，
这个标题不暗示它们不可变。大类数量也不必固定——记录多了可以把「能力与身体状态」
拆成两类，现在合在一起也够用。

## 一条记录怎么落到大类

按顺序取第一个可用的：

1. **人工移动**（`property_categorization` 记录）——最后一次移动生效；
2. **提取时写的分类**（`property_value.category`）——模型按当时的分类表选的；
3. **属性名推断**——`height` → 外貌、`holder`（物品）→ 归属与持有；
4. **取值推断**——只对 `state` / `status` / `condition` 这类说不出方面的名字：
   `脸色铁青` → 外貌、`心急如火` → 心理与意图、`身体慢慢地冒出金光` → 能力与身体状态；
5. **其他**——以上都不成立时。

推断结果带 `category_source`（`manual` / `extraction` / `name` / `value` / `fallback`），
界面上「其他」后面加 `?` 提示这是没定下来的。

推断依赖分类表本身：属性名推断出来的大类如果在当前表里已经不存在了，就退回「其他」，
不会硬塞进别的大类。审计会汇总有多少条落在「其他」，一次给一条提示。

## 一个方面一条线

一个方面 = 属性名的第一段（`cultivation_stage` → `cultivation`）。同一个方面下的全部记录
按披露顺序排在**一行**里，行首是仍然有效的那个值：

```
修为 · 到了元婴初期            声称/认知/世界   能力与身体状态
  同一方面 cultivation / cultivation_stage
  失效  修为      灵寂期      事件 老周告知林舟已到灵寂期 · 第二章 位置 3611 · 失效于 林舟吃猪肉脯…
  失效  修为境界   辟谷期      事件 林舟吃猪肉脯… · 第三章 位置 3479 · 失效于 林舟睁眼发现…
  有效  修为境界   到了元婴初期 事件 林舟睁眼发现满天星内甲缩入体内… · 第三章 位置 5004
```

有效/失效是记录上的标记，不是按位置算出来的区间：谁取代了谁由审核轮判定并写成
`property_retraction`（带 `event_id`），在那次披露之前读到的读者看到的仍是旧值。

属性区有两个范围，**不能互相代替**：

- **最新**：这一刻（当前阅读位置）仍然有效的记录。失效的不列出，只在副行写「N 条已失效」。
- **全部**：到这里为止的每一次披露，失效的也列出来，逐条标「有效 / 失效」并写明失效于哪次披露。
  这是历次状态的并集，不是「最新的另一种说法」。

两者在「失效」出现之前恰好相同，所以早先的界面把「最新」写成「最新（全部披露）」；
现在失效可以不靠新值发生，两个问题就必须分开问。

- **作用域是记录上的标签，不是拆行的理由**。世界说辟谷期、老周说灵寂期、林舟自知元婴初期，
  是同一件事的三次披露，不是三个同时成立的境界。
- 换了属性名（`cultivation` / `cultivation_stage`）不会多出一行，但那一行会写明
  「同一方面 cultivation / cultivation_stage」，每条记录也标出自己用的名字。
  这仍然是要修的：审计报 `name_variant`，确认同义后合并成一个名字。
- 前后值不同是**推进**，不是矛盾；只有同一名字、同一作用域、同一披露位置上的不同值
  才算重复（`duplicate_value`）。
- 位置数字跨章不可比，所以记录上带章节名（`source_title`）。

## 同一属性可以分在两个大类下

`state` 这种宽泛名字本来就装着不同方面。同一条属性按记录分片显示：
每片只带自己那几条记录，并注明「也在「X」中」，避免看起来像记录丢了。

这是**允许的**，不是需要立刻消灭的混乱。先把记录放到合适的位置，属性名以后再校对。

## 移动分类

- 入口：属性行的分类标签（整条属性一起移）、展开后每条记录的分类标签（只移这一条）。
- 实现：追加一条 `property_categorization` 记录，指向那条取值记录。记录只追加，
  不改写；撤回这条分类记录就回到上一种归法。
- 人工动作即时生效（人已经做了决定），但仍走同一条追加链，审计可回查。

## 改分类表

「分类表」按钮编辑当前节点类型的大类，一条一行，顺序即显示顺序。

改名会**迁移**：原位改名（旧名消失、新名出现，一对一）时，原本归在旧名下的记录
追加分类记录跟到新名下。整表重写不做这种猜测——那些记录会退回「其他」，
由审计提示，人工再放。

## 从两端看同一条记录

`铜钥匙 · holder = 老周` 一条记录，两个入口：

- 手镯页面：「归属与持有」；
- 老周页面：「反向引用」下的「持有与使用」。

同一条记录、同一个披露位置、同一段原文，没有复制，也不需要两边维护。
反向大类映射目前只覆盖 `归属与持有 → 持有与使用`、`关联 → 关系`（人物侧），
其余沿用原名；对不上就落到「其他」。

## 补录与纠正

- **补录**：属性区右上「补录」写一条披露（属性名、值、披露事件、大类、来源、原文引文）。
  **预检通过即生效**：人工写一条记录本身就是接受动作，模型输出才需要到「审核」接受。
  引文逐字复制后，披露位置由程序在原文里定位，不用人填；引文出现多次会被拒绝，要求写长一点。
  属性名第一次出现时自动补一条 `property_definition`（`value_type = any`）。
  同一方面更早的值从这次披露起失效——规则与提取、审计共用，不需要再点一次。
- **披露事件默认是当前阅读位置**：停在事件 A 就默认落在 A，而不是第一个事件；
  停在「最新」时沿用原记录的事件（更正）或第一个事件（补录）。
- **纠正**：节点类型、名称、别名、原文位置、撤回走「提交类型修订」，
  同样立即生效。改分类不是纠正——它不改内容。

## 按阅读位置看状态

数据浏览顶部两行条件，全部交给后端 `browse_view` 计算，界面只渲染：

- **事件等级**：`场景`（默认）或 `事件`。它决定「阅读位置」里列的是 20 个场景还是 81 个事件。
  场景是容器，**读完一个场景 = 读到它最后一个事件**，所以场景切点锚在最后一个子事件上；
  事件切点就是它自己。换粒度会把切点清回「最新」（旧切点不属于新粒度）。
- **全部显示 / 按时间显示**：控制节点列表要不要跟着阅读位置收窄。收窄后左侧分类计数
  同步变小；选中的节点如果还没出场，详情一起清掉。
- **阅读位置**：下拉 + `‹ / ›` 步进（顺序 1 → N → 最新，两端禁用）+ 「最新」一键复位。
- **相关节点**：勾选后只列当前这一步相关的节点——事件取它的参与者，场景取它内部
  所有事件的参与者并集，再加上这一步本身。

属性区（始终跟着切点）：

- 只显示该事件及之前披露的记录，之后的一律不显示，行上写「此后还有 N 条披露」，
  面板顶部写「读到「X」时的状态（第 n / N 个场景）；此后还有 N 条披露未显示」。
- **反向引用也跟切点走**：令牌是后文才记到林舟名下的，读到这里时林舟页面上不会出现它。
- 这是**阅读位置**，不是故事时间：它回答"读者读到这里知道什么"，
  不回答"那时世界里是什么样"（后者要 `applies_to` 那条链，还没建）。
- 记录仍然按披露顺序排；切点之前的记录里，失效标记同样按位置生效：
  切点早于「取代它的那次披露」时，旧值仍然有效。

列表收窄是**跨章**的：切点在第几章，后面章节的节点一律不出现（`revealed` 用
`source_orders` 判断章节先后，同一章内才比位置）。

### 这一层在哪

`src/narrative/browse_view.py` 是唯一的地方：步骤表（按粒度）、场景锚点、相关节点、
可见性、过滤、计数、切点解析都在这里，`Operations.browse_view` 只是把快照喂进去。
QML 提交 `{granularity, cut_id, node_type, query, related_only, time_filter}`，
拿到 `{nodes, counts, total, steps, events, cut}` 就画——不再自己过滤、计数或推导顺序。
`tests/test_browse_view.py` 直接测这一层，不需要起界面。

**计数跟着条件走，只除了类型筛选本身**：阅读位置、相关节点、搜索都会让计数变小
（否则数字和列表对不上），而类型筛选不参与——侧栏就是那个筛选，只剩一个类型就没意义了。

## 归并属性名

同一个方面用了两个名字（`cultivation` / `cultivation_stage`）时，那一行会出现
「合并…」入口：选一个保留，其余按它读。

- 归并是**读时别名**（`property_merge` 记录：`alias_id` → `target_id`），记录本身不改名，
  旧名字的定义也还在，所以旧记录仍然有效。
- 归并只改“读作哪个方面”，不改取值、不改分类、不改披露顺序；撤回这条记录就恢复成两个名字。
- 它和移动分类是两件事：一个改含义，一个只改位置。界面上也是两个入口。
- 归并之后审计不再报 `name_variant`，同一方面的值差异按一条时间线解释。

## 节点编辑器

详情面板右下角「编辑节点」打开，一个节点一份：

- **节点字段**：名称、类型、别名、说明 → 「提交节点修订」走候选。
- **属性**：按方面列出这个节点的记录（有效 / 已失效 + 失效于哪次披露、原因）。
  停在「最新」时看整份历史；**按阅读位置看时只列那一刻已经读到的记录**，之后的披露不显示
  （顶部写明「此后还有 N 条未显示」）。**编辑照旧可用**：改动立即生效，落在你选的披露事件上；
  如果那个事件在当前阅读位置之后，提示会写明「它披露于 X，切到最新或那个事件才看得到」，
  而不是让改动看起来没发生。
- **新增属性**：复用补录表单（属性名、值、披露事件、大类、来源、引文）。
- **更正**：改的是"追加一条新披露"，不是原地改值。可以勾「同时把原记录设为失效」，
  新记录与撤回进同一个候选，不会只落一半。
- **失效**：把这条属性的记录一起标为失效，**原因必填**。失效不删行——浏览区不再显示它，
  编辑器仍然看得到是哪条、为什么撤。

所有改动都先成为候选，到「审核」接受后才生效；编辑器不直接写正式资料。

## 不做的事

- **不自动合并属性**。`identity` 与 `title`、`appearance` 与 `state` 是否同义，
  要先确认含义相同再手动归并；分类宽松，归并要严。归并是单独的操作，可撤回。
- **不改取值**。分类记录和归并记录里都没有值，也没有原文引文——它们不是披露。
- **不因为分类而拆分属性**。`state = 衣服破烂` 和 `state = 身受重伤` 仍是同一个 `state`，
  只是显示在两个大类下。
- **不要求每条记录都分对**。拿不准就留在「其他」，不影响取值、查询和披露顺序。

## 审计

`property_audit` 里与分类有关的只有三条：

| 代码 | 级别 | 含义 |
| --- | --- | --- |
| `category_unknown` | warning | 记录的分类名不在该节点类型的分类表里（改名或删类之后） |
| `category_unassigned` | info | 全库有多少条落在「其他」，一条汇总，不按记录刷屏 |
| `categorization_target_missing` | error | 分类记录指向的取值记录不存在 |

## 真实模型验证（2026-10-25）

改动涉及提取提示词，按约定做了一次有界验证：隔离工程
`data/verify-categories/verify.sqlite3`，输入为第一章前 900 字（`excerpt.txt`），
`ark` / `ark-code-latest`，单次请求（`completion_tokens` 16943，其中推理 13984；
`prompt_tokens` 3348），原始响应与 usage 见 `data/extraction/verify-categories/`。

结果：19 条属性全部带分类，且分类跟着对象类型走——

| 记录 | 分类 |
| --- | --- |
| 苏娘 · `appearance` = 千娇百媚的美女 | 外貌 |
| 林舟 · `state` = 心里对女人有点发怵 | 心理与意图 |
| 林舟 · `state` = 目瞪口呆 | 其他（模型自己拿不准，按约定留「其他」） |
| 苏娘 · `state` = 被说中痛处 | 心理与意图 |
| 桃红色烟障（物品）· `state` = 上下浮动显得十分诡异 | 状态 |
| 桃红色烟障 · `ability` = 犹如活物般躲避 | 功能与特性 |
| 传送阵 · `user` = 林舟 | 归属与持有 |
| 十一个死鬼兄弟（群体）· `count` = 11 | 构成与规模 |

工程里预置的 `state` 属性名被沿用（提示词的「已有属性名」段生效），
第二轮把同位置重复的 `老周.state` 判为重复丢弃。
这一次验证只覆盖提示词与分类落库，没有覆盖人工移动与改表——那些由自动化用例覆盖。

## 代码位置

- `src/narrative/property_categories.py`：默认分类表、名字/取值推断、方面（`aspect_of`）、
  改名检测、配置读写。
- `src/narrative/property_labels.py`：属性名的中文显示名（`height` → 身高）。
  只影响显示，不改数据；不认识的属性名照原名显示。
- `src/narrative/property_store.py`：`node_properties`（按方面 + 大类分行，记录带章节名）、
  `categorize`（移动）、`set_categories`（改表 + 迁移）。
- `src/narrative/property_core.py`：`property_categorization` 记录的字段与校验。
- `src/narrative/property_audit.py`：分类相关三条 + `name_variant`（同一方面多个名字）。
- `src/narrative/extraction.py`：提示词带分类表和工程里已有的属性名，每条属性要求给 `category`。
- `src/narrative/qml/PropertyItem.qml`、`BrowsePage.qml`：分组显示、分类标签、分类表对话框。
