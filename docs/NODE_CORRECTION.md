# 节点修正（在界面里改，不靠脚本）

## 为什么需要

模型抽取会出错：把修炼境界当成事件、把口头语当成人物、给节点挂错类型。
如果每次都要写脚本改数据库，这些错误就只能由开发者修——**产品本身没有纠错能力**。

所以修正入口做在节点详情面板里，和候选审核走同一条链路：
改动先生成候选，人工接受后才进正式图。

## 三个操作

| 操作 | 界面位置 | 生成的对象 |
| --- | --- | --- |
| 改类型 | 节点详情 · 类型下拉 + 「改类型」 | 同 ID 的 `node`，`node_type` 变更 |
| 标为阅读位置 | 节点详情 · 「标为阅读位置」 | 同 ID 的 `node`，写入 `disclosure` |
| 撤回节点 | 节点详情 · 「撤回节点」 | 同 ID 的 `node`，`retracted=true` |

「标为阅读位置」取当前阅读进度（上方阅读进度下拉选中的位置），不是随便点。

桥接入口：`NativeBridge.reviseNode(nodeId, changes)`，`changes` 只接受
`node_type` / `name` / `aliases` / `identity_note` / `disclosure` / `retracted`。

## 撤回不是删除

`retracted=true` 的节点保留在 `objects` 表里，历史修订仍能查；
只是所有投影（`graph_query`、层级、时间轴、候选预览）不再返回它。

这样"这个实体不存在"可以事后复核：谁在什么时候撤回的、撤回前它挂过什么，都还在。

## 一次真实修正

三章项目里这批问题是通过上面的能力改的（不是直接写库）：

| 节点 | 原来 | 改为 | 依据 |
| --- | --- | --- | --- |
| 天劫 | event | other | 原文「不就是渡个天劫吗」 |
| 灵寂期 | event | other | 「这么短的时间就到了灵寂期」 |
| 合体期 | event | other | 「你要修真到合体期」 |
| 落英阵 | event | other | 苏娘的招式名 |
| 万花罩 | event | item | 苏娘的护身法宝 |
| 身体改造 | event | other | 概括词，原文无对应表述 |
| 火星传送阵 | event | location | 第二章场景，林舟坐在传送阵里 |
| 上帝 | person | 撤回 | 只是林舟口语里的称呼 |
| 阿弥陀佛 | person | 撤回 | 祷告时的口头语 |
| 老周对苏娘的战斗 | 无位置 | 第三章 1446 | 苏娘出「落英阵」起手 |
| 古代中国人被传送至云顶星 | 无位置 | 第三章 3998 | 古人分四批被传送 |

结果：可见节点 82 → 80，事件 17 → 10，其中 8 个有原文位置。

## 测试

`tests/test_native_bridge.py::test_bridge_revises_node_type_and_retracts`
覆盖三条路径：改类型 → 候选 → 接受后生效；撤回 → 查询不再返回、历史仍保留；
写位置 → 落到节点上。全部通过桥接调用，不直接操作数据库。
