# 数据模型

v6 图项目。两层：来源、对象。对象之间不再有断言层——时序与组织关系已删除，
逻辑事件图留到第二阶段重建。

一句话定义：

> **从整章原文直接提取对象、事件与属性披露。每条记录以原文证据和披露位置定位；事件提供阅读区段的锚点，并用于组织情节。阅读顺序直接建立，故事时间与逻辑适用关系在有依据时补充。**

## 两条链，不能混

这是本模型最容易出错的地方。系统里同时存在两种"顺序"，它们回答不同的问题，
**不能共用一个字段，也不能互相推导**。

| 方面 | 披露事件链 | 逻辑事件图（事件池） |
| --- | --- | --- |
| 回答 | 原作依次向读者披露了什么？ | 故事里的事情怎样发生、什么关系？ |
| 结构 | 对确定版本，**完全线性** | 允许平行、分支、合并、孤立，部分顺序未知 |
| 依据 | 章节顺序 + 原文位置 | 原文明确陈述的关系，以及有依据的推理 |
| 存不存 | **不存**，节点 id 本身就是顺序 | 存在 `predecessors` / `successors` |
| 属性锚点 | 到这里，该信息进入读者可见记录 | 该属性在什么故事事件处适用（`applies_to`，暂空） |
| 遇到插叙 | 按实际出现位置登记 | 关联到较早发生的事件（第二阶段） |

因为披露链不存储，所以"链断了"只可能是逻辑图的边没建立，不是阅读顺序出了问题。

**事件之间不需要任何"前后关系"字段**：节点编号就是披露位置，`1 < 2 < 3` 就是阅读顺序。
跨章也不需要额外的章序参与比较——第一章 `1…71`、第二章 `74…110`、第三章 `113…164`，编号本身就连着。

**同一个事件内部**则要用记录自己的原文位置：一个锚点可以有多条披露（复述、改口、矛盾），
编号相同，只能靠 `disclosure.start` 定先后。

```text
（事件编号，同一事件内的原文位置）
```

所以"最近披露"是排序后的最后一条，**不是最后写入的那条**——补录一句更早的话，
它不会变成最新的说法。

### 映射不是一一对应

同一个故事事件可以被披露多次（回忆、复述），同一段披露也可以涉及多个故事事件。
所以：**确认两次披露是同一次事件时，合并的是逻辑身份，两次披露的位置与证据都保留。**

## 对象层：Node

| 字段 | 作用 | 说明 |
| --- | --- | --- |
| `id` | 主键 | 多段整数编号，值就是披露顺序（`1`、`2`、`1.1`）；改名不改 id |
| `node_type` | 八类 | `person` `group` `item` `location` `scene` `event` `storyline` `other` |
| `name` / `aliases` | 名称与别名 | 名称用原文最常见称呼，其余进 aliases |
| `context_id` | 世界分支 | 默认 `canon`；假设、不同版本用它区分（不是认知范围，认知用 `scope`） |
| `disclosure` | 读者在哪读到 | `{source_id, start}`，**不需要推断** |
| `evidence` | 它来自哪句话 | `{source_id, quote}`，引文须是原文子串 |
| `occurrence` | 故事时间 | 仅事件；可选，没把握就留空 |
| `participants` | 参与者 | 仅事件；引用人物/群体/物品/地点的节点 id |
| `predecessors` / `successors` | 逻辑事件图的边 | 仅事件；可多前驱多后继（分支、合并） |
| `events` | 子事件 | 组合事件专用：场景包含原子事件，场景之上还能再套一层 |
| `retracted` | 撤回 | 保留历史，投影里消失 |

### 章节只是标记，不是断点

全书一条披露序列，**编号跨章连续**，换章照常追加。章节信息挂在事件上：

```json
{"id": "2", "node_type": "event", "name": "沈砚告知林舟陈默来电",
 "source_marks": [{"source_id": "…", "role": "start"}]}
```

`role` 只能是 `start` 或 `end`，且只挂在事件节点上。它用于显示章节标题、跳转、筛选，
**不触发属性重置，也不切断披露链**。

新章开头若先有说明、还没出现新事件，属性可以继续挂在前一个披露事件上，
自己的 `disclosure` 仍然记录精确位置。

### 编号规则

节点主键就是它在披露链上的位置，所以排序不需要额外字段：

```text
1 < 1.1 < 1.1.1 < 1.2 < 1.10 < 2
```

逐段按整数比较，前面各段相同时较短的在前。点只是分隔符，**不代表父子或包含关系**。

| 情况 | 分配 |
| --- | --- |
| 首次顺序提取 | `1`、`2`、`3`…… |
| 在 `1` 与 `2` 之间补录 | `1.0.1`（再插一个：`1.0.2`） |
| 在 `1.1` 与 `1.2` 之间补录 | `1.1.0.1` |
| 在第一个节点之前补录 | `0.1` |

插入一律用 `prev.0.k`：这是唯一既排在 `prev` 之后、又排在其后那个编号之前的形状。
不能用 `prev.1`——`1.1` 已经排在 `1` 之后了，再加段只会更靠后。

中间段允许为 `0`，**末段必须大于 0**：`1.1` 与 `1.1.0` 之间没有可用的非负整数分段，
禁止末段为零才有继续插入的空间。每段不留前导零，`1.01` 与 `1.1` 只保留后者。

补录只加段，已有编号不变，不重排。同一记录重跑读回原编号，失效编号不回收。
比较一律用 `order_ids.order_key()`，**不能按字符串排序**（否则 `1.10` 会排在 `1.2` 前面）。

### 身份规则

名称和类型只能帮你找到匹配候选，**不能判定是同一个人或同一次事件**。

| 情况 | 处理 | 记录 |
| --- | --- | --- |
| 类型、名称、引文、来源、位置都相同 | 同一条提取记录，重跑读回原 id | — |
| 同批内同名同类型、引文不同 | 两次不同的出现，各自独立 | — |
| 跨批同名同类型，库里只有这一个 | 复用（唯一名称） | `decision: "reused"` |
| 跨批同名同类型，库里已有多个 | **不合并**，新建独立节点 | `decision: "separated"` |
| 事件 | **从不按名字复用** | — |

事件尤其不能按名字合并：两处都叫"林舟修炼"，可能是两次不同的修炼。

**UUID 不会自动修好误合并。** 主键换掉了，但如果代码仍按名称找已有节点并复用，两个同名对象
照样会合到一起。所以复用条件收窄为"全项目仅此一个同名同类型节点"，并且这次复用要留痕。

`identity_candidates` 随提取结果保存，每条给出 `decision`（`reused` / `separated`）、
两边的节点 id 和证据位置。**它是事后记录，不是确认**——确认入口还没做。

## 断言层已删除

`PredicateDefinition` / `Assertion` / `Evidence` / `EvidenceLink` 模型、`evidence_links` 表、
`temporal` 偏序、`containment` 组织树、关系图、路径搜索、`graph_hierarchy` 全部移除
（schema 5 → 6，旧库直接拒绝打开）。

现在图里只有节点、语境、时间轴、来源顺序和属性记录。场景与事件的包含关系用节点字段
`events`——一条记录说清"这个场景里有哪些事"，不另建边。

属性记录有六种：`property_definition`、`property_value`、`property_categorization`、
`property_merge`、`property_rename`、`property_retraction`。旧的 `property_initial` / `property_observation` / `event_change`
已从代码中删除——包括校验、求值和示例。前期开发不保留兼容路径，留着只会让人误以为还能用。

## 陈述层之二：属性记录

属性是**一条序列**，每个元素是 `(值, 披露检查点)`。

| 记录 | 作用 |
| --- | --- |
| `property_definition` | 值类型、基数、持续性 |
| `property_value` | `node_id` + `property_id` + `value` + `event_id` + `anchor_basis` + 可选 `applies_to` / `source` / `related_nodes` / `scope` / `holder_id` / `category` + 证据 |
| `property_categorization` | 把某条取值记录移到另一个显示大类：`target_id` + `category`。整理动作，不是披露，没有证据 |
| `property_merge` | 两个名字读作同一个方面：`alias_id` → `target_id`。读时别名，记录不改名 |
| `property_rename` | 一个方面换个名字：`from_id` → `to_id`。读时别名，定义跟着搬到新名字 |
| `property_retraction` | 把序列里的某一条设为失效：`target_id` + `reason` + 可选 `event_id` / `disclosure` / `basis` |

归并和改名都**不改写取值记录**：记录保留采集时的名字，投影按别名读。
区别在定义：归并让旧名字继续作为独立定义存在（它仍然是那个方面的一个拼法），
改名把定义搬到新名字下（形状沿用），所以改名可以落到一个还不存在的名字上，
而落到另一个方面的名字上会被拒绝——那是归并，不该静默发生。

`property_retraction` **没有自己的节点和属性名**：它是编辑动作，不是披露。
节点、方面、作用域一律从 `target_id` 指向的那条记录读，两处因此不会互相矛盾。
有没有 `event_id` 是两种不同的失效：

- **没有 `event_id`**：这条记录读错了，它在任何阅读位置都不算数。
- **有 `event_id`**：记录当时是对的，但从这个披露起不再是状态的一部分（被后一条取代）。
  在这个位置之前读到的读者，看到的仍然是旧值——这是唯一有意义的阅读顺序。

**有效期不再计算。** 一条值什么时候结束，由这条失效记录说，不由「下一条披露」推出来。
投影只回答两件事：这条记录现在还有效吗（`valid`）、它在哪个披露失效（`invalidated_at`）。

**失效只有一个结果：不显示。** 撤回不删行——记录还在库里、审计还能看到——但它不再出现在
节点的属性里：没有「已失效」标记，没有失效条数，也没有「失效于哪次披露」。一条记录只有
一个字段回答这件事：还算不算数（`valid`），不算就不出现。

`invalid_at` 是沿披露链的一次折叠：每条失效从自己的位置把记录拿出去，`cut` 决定折叠到哪一步。
界面上的「失效」落在读者当前站的位置（停在「最新」就是最后一个事件），
「读错了，从来不算」走更正那条路（追加新值 + 撤回旧值）。

失效与另外两种情况不是一回事：

- **还没读到**——阅读切点之外的披露。它们既没失效也没过时，只是读者还没读到，
  界面上以「此后还有 N 条披露」计数，不显示。
- **读错了**——见上面没有 `event_id` 的失效：行保留供审计，编辑器仍看得到原因。

**被取代是自动的。** 一批记录被接受时，`accept` 在同一个事务里按披露顺序把更早的值标成失效
（同节点、同方面、同作用域、同持有人的单值属性；重申不算取代；同一个事件里说了两个值算并列，
不互相取代）。它和引起它的那次披露属于同一个版本，不需要人再去点一次「应用建议」。

人只需要判一件事：这条**从来没有算数**（读错了）。那是不带 `event_id` 的失效，走更正那条路。

`category` 只管显示位置，与 `scope` 各管一件事；分片规则与移动方式见
[`PROPERTY_CATEGORIES.md`](PROPERTY_CATEGORIES.md)。

### `event_id` 是什么

**它是披露检查点，不是变化原因。**

以年龄为例：

| 读到的检查点 | 原文 | 查询结果 |
| --- | --- | --- |
| E1 人物出场 | 尚未提到年龄 | `unrecorded` |
| E5 介绍经历 | "他今年二十九岁" | 29 |
| E8 与人交谈 | 没有新的年龄信息 | 仍是 29 |
| E20 明说两年后 | "如今已经三十一岁" | 31 |

在 E5 登记 29，含义是"从 E5 起，系统有了这条记录"。它**不表示**人物在 E5 才有年龄，
也不表示 E5 让他变成 29 岁。E8 继续返回 29，表示仍以这条已披露信息为依据。

同一个字段不能有时表示披露位置、有时表示真实生效时间。既然主线采用披露锚点，就始终按这一种解释。

原文明确写了变化，把变化作为内容记录即可，不改变锚点字段的含义。

### 锚点怎么定

事件提供**阅读区段的锚点**，原文位置决定信息究竟何时可见。

| 情况 | 处理 | `anchor_basis` |
| --- | --- | --- |
| 模型点名了事件且能对上本章事件 | 用该事件 | `model` |
| 位置落在某个事件的叙述范围内 | 用该事件 | `nearest` |
| 位置在两个事件之间 | 用**最近的前置事件** | `nearest` |
| 位置在本章第一个事件之前 | 归入本章开篇区段（第一个事件） | `nearest` |
| 位置在本章最后一个事件之后 | 挂最后一个事件 | `nearest` |

**不需要为"介绍年龄""介绍籍贯"另建事件**，也不需要新增检查点节点。章末补充的信息不会因为
后面没有事件就被丢掉。

`anchor_basis` 说明**谁选的锚点**，不说明原文给出了故事生效位置。`model` 只是"模型点了这个事件"。

**不会回填到全书起点。** 后文首次披露的属性挂在后文节点；挂到"故事开始"会让读者在第一章开头
就看到第三章才知道的信息。

`disclosure` 与 `event_id` 并存：前者是精确的字符位置，用于切点过滤；后者是组织单位，用于按节点查询。
同一事件区段内，属性自己的 `disclosure` 能区分"读到 120 时还没披露、读到 160 时已披露"。

### 一条记录 = 一次披露

属性序列里没有"变化记录"这种东西。**一条新记录本身就代表这次披露**——可能是首次、
确认、或改口，不需要另建记录类型，也不需要标注"这是变化还是状态"。

属性名描述**被说的那个方面**，不描述变化，**也不因为值形态不同就另起名字**：

| 原文 | 记录 |
| --- | --- |
| "他身高矮小" | `height = 矮小` |
| "自己一定是变高了" | `height = 变高了` |
| "足有一百八十公分" | `height = 180` |

三条都挂在 `height` 上。不写 `height_change`（那是变化，不是方面），
也不写 `height_cm`（那是数值，不是另一个方面）。

`property_definition.value_type` **不参与校验**（只有 `node` 类型会检查引用是否存在）。
声明为 `string` 的属性记一个 `180` 不会报错——记录本来就是多样的，不必先满足类型系统。
`any` 可以写，但已经没有实际作用。

数值带单位就直接写进值里：`height = "180 公分"`，不另建数值/单位/文本三套结构。

### 作用域：三类，不互相转换

一条记录属于哪一层，由 `scope` 说明；`holder_id` 说明**是谁**持有这条信息。两者不重复。

| `scope` | 表达 | `holder_id` |
| --- | --- | --- |
| `world`（默认） | 按原文叙述登记在世界层面 | 不填 |
| `cognition` | 某个人怎样理解、相信、知道、记得、怀疑 | 认知者 |
| `claim` | 某个人对外说出的内容 | 表达者 |

「知道」归入 `cognition`，不单开一类——否则「甲以为乙二十岁」和「甲得知乙二十九岁」
会落进两条互不更新的历史，查 `belief` 永远得到旧值。原文的确定程度照抄进 `value`，
不把"怀疑"改写成"确定"。

三条互不转换：

- 说了（`claim`）不等于相信（`cognition`）
- 相信不等于世界成立（`world`）
- 世界改变不等于人物已知道

**`world` 只是"登记在世界层面"，不是"经过系统认证的真相"。** 原文会矛盾，模型会提错，
叙述可能有意误导，这些都还能校对。

### 来源与关联

| 字段 | 作用 |
| --- | --- |
| `source` | 信息是怎么表达出来的：`narration` / `speech` / `thought` / `observation` / `document`，自由字符串，拿不准留空 |
| `related_nodes` | 原文明示涉及的其他节点：观察者、被归因的人、信息载体。**不含 holder** |

例：「A 看见 C 受伤，认为是 B 干的」

```text
C.伤势 = 受伤            scope=world  source=observation  related_nodes=[A]
C.伤势 = B 造成          scope=cognition holder=A  source=thought  related_nodes=[B]
```

第二行没有把「B 造成了伤」提升成世界记录——原文只说 A 这么认为。
两条都能从 A、B、C 三个节点反查。

### 允许模糊与并存

属性记录**不要求精确**。这些都合法：

| 原文 | 记录 |
| --- | --- |
| "身高一百八十公分" | `height_cm = 180` |
| "他又长高了一些" | `height_change = 变高了`，幅度未说明 |
| "伤势有所好转" | `injury = 好转，未说明是否痊愈` |
| "神色似乎更差" | 保留"似乎"的不确定语气 |
| 两处写 180 和 175 | 两条都留，各自带出处，供校对 |

同一个节点上并存的三条：

```text
height = 180      @ 二 · 139
height = 矮小      @ 一 · 270
height = 变高了    @ 一 · 3567
```

按披露顺序读到最后，`height` 是「变高了」。想知道"有没有明确数值"，就查序列里最近一条
`int` 类型的记录——是 180。不需要在提取阶段判定谁替代谁，也不需要先算出"现在到底多高"。

### 求值

```python
property_event_state(node, property, event, axis="disclosure")   # 默认
property_event_state(node, property, event, axis="story")
```

| 轴 | 适用记录 | 结果 |
| --- | --- | --- |
| `disclosure` | 披露位置 ≤ 目标事件的记录 | 取**最近**的一条。线性，无需推理 |
| `story` | 只认带 `applies_to`（明确的逻辑适用事件）的记录 | 有则求值；没有则返回 `unlinked` |

故事轴**不借用披露锚点**。"读到 D70 时人物回忆十岁住在山村"——属性在 D70 进入读者可见记录，
但这不能推出 D70 对应的故事事件发生时他住在山村。

没有 `applies_to` 的记录一律返回：

```json
{"kind": "unlinked", "reason": "尚未建立属性与逻辑事件的适用关系，无法据此求故事状态"}
```

这是如实说明，不是失败。`applies_to` 现在全部为空——逻辑关联属于第二阶段。

故事轴也**不按祖先数量当深度**：分支上多走几个无关事件，不代表那条记录更晚。分支给出不同值时
返回 `divergent` 并列出候选，不硬选。

## 提取方式：三轮

```text
原文整章
   │
   ├─ 第一轮  读整章 → 节点 + 事件 + 属性（不知已有数据）
   │
   ├─ 第二轮  本批属性 + 这些属性的当前值 → keep / drop / unsure
   │
   └─ 第三轮  只处理 unsure：完整属性历史 + 原文上下文 ±120 字 → 终判
```

**第一轮**：一次调用读完一章，输出六类节点和属性。引文必须逐字复制，
程序逐字比对，对不上的丢弃并记原因。

提取**不产出事件之间的先后关系**。逻辑图（谁先谁后、谁包含谁）留给第二阶段，
本阶段只做披露：内容、位置、证据、编号。

**说明性内容也是披露。** 法宝是什么、星球叫什么、人物有什么经历，这些段落没有动作，
但都是原文明确告诉读者的信息，必须提取。曾经漏掉「老周展示并解释纳芥手镯」和
「林舟阅读岩壁文字，得知星球叫云顶星」，就是按"有没有动作"筛的后果。

**第二轮**：宽松保留。**只丢弃确定的重复**——同一原文位置、同一个值重复输出了两遍。

| 情况 | 处理 |
| --- | --- |
| 同一位置、同一个值重复输出 | 丢弃多出来的那条 |
| 不同位置披露同一个值 | 保留（新的确认，有独立出处） |
| 属性名不同但意思接近 | 各自保留，不改名，留给校对归并 |
| 值不同、模糊描述、疑似矛盾 | 全部保留 |
| 拿不准 | 保留 |

理由：误删会丢掉原文信息，重复只是多一条记录。**去重不承担"统一事实"的任务。**

**第三轮**：只针对 `unsure`，给出该属性完整历史 + 原文上下文，强制终判。仍存疑的进 `unresolved`，
保留但标记，交给人工。

模型可返回 `{"need": [...]}` 要求追加信息，总轮次上限 4。

## 三条轴，各管一件事

| 轴 | 数据 | 回答 | 现状 |
| --- | --- | --- | --- |
| 披露 | `(节点 id, 同一事件内的原文位置)` | 读者先读到谁 | 完整，线性，无需额外字段 |
| 逻辑 | `predecessors` / `successors` | 故事里谁先发生 | 全空，第二阶段填 |
| 故事时间 | `occurrence` | 具体何时发生 | 空 |

事件比较按轴调用：

```python
graph_event_compare(a, b)                  # 披露顺序：before / after / same
graph_event_compare(a, b, axis="story")    # 故事先后：before / after / parallel / contains / unknown
```

返回里的 `axis` 和 `basis` 说明这个结论从哪来：

| `basis` | 含义 |
| --- | --- |
| `disclosure` | 按原文披露位置（线性） |

故事轴现在没有数据来源：`axis="story"` 一律返回 `unknown`。逻辑图上不可达**不等于**同时发生，
只表示"先后关系尚未建立"。

## 旧合同如何接进来

这些能力都还在代码里，只是没写进本文件。

| 能力 | 位置 | 与 `property_value` 的关系 |
| --- | --- | --- |
| 作用域 `scope` / `holder_id` | `property_core._SCOPES` | `world` / `cognition` / `claim`。**世界与认知即使值相同，也是两条记录**；不同人物持有同一认知也不合并 |

| 历史修订查询 | `revision` + `as_of_revision` | 任何查询都能回到旧修订 |
| 依赖失效 `derived_from` / `support_groups` | `property_core._DEPENDENCY_FIELDS` | 上游记录撤回时，依赖它的记录被标记失效 |

## 两阶段路线

**第一阶段（当前）**：完成原作披露链。提取事件、实体、参与者、属性；每条带证据、来源位置、

第二阶段不能只读压缩后的事件标题——证据和原文上下文必须仍然可访问。
